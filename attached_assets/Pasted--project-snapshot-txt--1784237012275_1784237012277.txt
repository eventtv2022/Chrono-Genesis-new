## 🛡️ Часть 1. Аудит безопасности и критические уязвимости

В текущей архитектуре бэкенда обнаружено несколько критических уязвимостей, которые необходимо устранить, чтобы исключить риск эксплуатации или манипуляций балансами пользователей.

### 1. Критическая уязвимость: Отсутствие проверки сессии (Authentication Bypass) в API аукционов

* 
**Где находится:** Файл `artifacts/api-server/src/routes/auctions.ts`, эндпоинты создания лота `POST /api/auctions` и размещения ставок `POST /api/auctions/:id/bid`.


* 
**Суть проблемы:** Эндпоинты принимают параметры `sellerId` и `buyerId` напрямую из тела запроса (`req.body`), обрабатывая их с помощью Zod-валидации. Однако в коде **отсутствует промежуточное ПО (middleware) для проверки токена сессии** (например, `ensureAuthenticated` или проверка сессионных кук).


* **Риск:** Злоумышленник, зная `id` любого другого гражданина (например, узнав его из публичного фида или списка транзакций), может отправить запрос от его имени. Это позволяет принудительно выставлять чужие Дармины на аукцион или делать ставки чужими деньгами без ведома владельца аккаунта.
* **Как исправить:** Добавьте middleware авторизации, которое будет извлекать ID текущего пользователя из проверенной сессии (например, `req.user.id`), и используйте его вместо данных из `req.body`:
```typescript
// Пример исправления:
const buyerId = req.user.id; // брать строго из проверенной сессии, а не из req.body

```



### 2. Уязвимость: Потенциальный Command Injection в рендерере видео

* **Где находится:** Логика экранирования строк для FFmpeg-скриптов. В коде присутствует функция `esc(s: string)` , которая заменяет одиночные кавычки на фигурные апострофы `\u2019` во избежание проблем со shell-цитированием.


* 
**Суть проблемы:** Если пользовательский ввод из `seedText` или `manifestoText` передается в системные вызовы командной строки (например, через `exec` или `spawn` без строгого разделения аргументов на массивы), замена кавычек может оказаться недостаточной для предотвращения инъекции команд через другие управляющие символы (например, символы перенаправления потоков или конвейеры).


* **Как исправить:** Полностью исключите передачу аргументов в виде единой строки в shell. Используйте `child_process.spawn` строго с массивом аргументов, где каждый параметр передается изолированно, минуя интерпретатор командной строки (`shell: false`).

## 📈 Часть 2. Ошибки бизнес-логики и математические расхождения

При анализе финансовых транзакций и работы с сеткой вещания на 1440 минут выявлены архитектурные нестыковки.

### 1. Расхождение при округлении налога в аукционах (Потеря Дарминов)

* 
**Где находится:** Файл `artifacts/api-server/src/routes/auctions.ts`, эндпоинт `POST /api/auctions/:id/finalize`.


* **Код проблемы:**
```typescript
const finalPrice = auction.currentBid ?? auction.startingPrice;
const tax = finalPrice * 0.02; [cite_start]// [cite: 10837]
...
const sellerReceives = Math.floor(finalPrice - tax); [cite_start]// [cite: 10839]

```


* 
**Суть проблемы:** Комиссия `tax` рассчитывается как число с плавающей точкой (тип `real` в БД). Однако при зачислении средств продавцу используется функция `Math.floor(finalPrice - tax)`, которая округляет сумму вниз до целого числа. При этом в лог аукциона `auctionLogsTable` записывается исходный дробный `tax`.


* **В чем баг:** Куда уходит остаток от округления `Math.floor`? Он просто сгорает в никуда, не зачисляясь ни на баланс Казначейства, ни на баланс продавца. Это приведет к постоянному расхождению общего баланса системы (суммы всех минут всех граждан) с общим объемом эмиссии.
* **Как исправить:** Избыток, остающийся после округления, необходимо явно переводить на системный аккаунт Казначейства, чтобы дебет с кредитом всегда сходился до сотых долей.

### 2. Угроза состояния гонки (Race Condition) при покупке тайм-слотов

* 
**Где находится:** Логика бронирования минут вещания `tvSlotsTable`.


* 
**Суть проблемы:** В схеме `tvSlotsTable` установлена уникальность на пару дата+минута, что защищает базу от дубликатов на уровне СУБД. Однако если два пользователя одновременно отправляют запрос на покупку одной и той же минуты, проверка статуса (`status === 'free'`)  у обоих может пройти успешно до того, как первая транзакция успеет зафиксировать изменение статуса в БД.


* 
**Риск:** Один из пользователей получит ошибку базы данных на этапе сохранения, но если с него уже списались Дармины или обработался внешний платеж (Stripe/Cryptomus), средства окажутся заблокированы или списаны ошибочно.


* **Как исправить:** Обязательно используйте блокировку строк при чтении (например, `FOR UPDATE` в PostgreSQL через Drizzle) или выполняйте списание и резервирование слота единым атомарным запросом:
```typescript
// Пример атомарного обновления:
await tx.update(tvSlotsTable)
        .set({ ownerId, status: 'booked' })
        .where(and(eq(tvSlotsTable.id, slotId), eq(tvSlotsTable.status, 'free')));

```

## 🎨 Часть 3. Аудит Web vs. Mobile (Синхронизация и UI)

По результатам анализа интерфейсных файлов фронтенда зафиксированы критические расхождения в поведении версий.

### 1. Расхождение в цветовом кодировании типов слотов

* 
**В Веб-версии:** Используются стандартные Tailwind-классы и динамические бейджи для типов минут (Apex, Half, Quarter, Citizen).


* 
**В Мобильной версии (Expo):** Цвета завязаны на объект `colors`, в частности, используются кастомные стили вида `colors.goldGlow` и жестко зашитые HEX-коды (например, фиатные платежи подсвечиваются зеленым кодом `#22c55e`). Из-за жесткого кодирования цветов в мобильном приложении на некоторых экранах (например, в темной теме оформления) текст становится нечитаемым.


* **Решение:** Вынесите всю палитру обозначения типов слотов в единый конфигурационный файл, общий для кроссплатформенной структуры, чтобы избежать расхождения визуального восприятия у пользователя.

### 2. Разница в обработке состояний сетки (Virtualization vs. Inline Render)

* 
**Веб-интерфейс:** Оптимизирован под префетчинг соседних минут (в коде присутствует интервальный таймер для упреждающего фонового запроса следующего слота `fetchSlot(next)`), что гарантирует бесшовное переключение сетки в реальном времени.


* 
**Мобильный интерфейс (Expo):** Отображает данные через компоненты листов и модальные шторки бронирования (`CalendarBookingSheet`). В мобильной версии отсутствует логика упреждающего фонового префетчинга минут, из-за чего при пролистывании сетки или открытии детальной информации о минуте возникает заметная задержка (интерфейс «подмигивает», ожидая ответа от API).


* **Решение:** Перенесите сервисную логику префетчинга и кэширования слотов, используемую на веб-страницах, в React Native контекст мобильного приложения.
